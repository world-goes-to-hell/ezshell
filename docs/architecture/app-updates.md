# 앱 업데이트와 탭 복원

[공통 작업 규칙과 기능별 목록](../../CLAUDE.md)

실행 중인 앱은 시작 3초 뒤, 30분마다, 창에 다시 포커스가 올 때(10분 간격) 새 버전을 확인한다 (`src/updateChecker.js`). 자동 확인은 새 버전을 찾았을 때만 화면에 알리고, 알림 닫기는 버전 단위다 (`updateStore` 의 `dismissedKey`). 설명: `docs/fix/2026-10-27-update-check-while-running.md`.

업데이트 뒤 처음 잠금을 풀면 본창에 "업데이트 내용"(`WhatsNew/WhatsNewDialog.tsx`)이 뜬다: main 의 `src/lastVersion.js` 가 `userData/last-version.json` 에 마지막으로 본 버전을 두고, 그 뒤 버전들의 노트를 최신순으로 보여 준다 (`lib/releaseNotes.ts`). `확인` 을 눌러야 기록한다. 새 설치는 띄우지 않고(새 설치인지는 앱이 시작할 때 정한다: 창이 묻는 때는 첫 잠금 해제 뒤라 마스터 비밀번호 파일이 이미 있다), 기록이 없는 기존 사용자(세션 파일 있음)는 지금 버전 노트를 본다. 명령 팔레트 `업데이트 내용 보기` 로 다시 연다. 설계: `docs/plan/2026-11-12-whats-new-after-update.md`.

Windows에서 업데이트를 받아 `재시작`을 누르거나 앱을 닫으면 모든 창이 닫힌 뒤 `will-quit`에서 `updates.js`의 종료 처리가 시작된다. 바꾸면 안 되는 것: 설치 프로그램을 실행하기 전에 `main.js`의 `finishSessionQuit`에서 앱 안에서 연 로컬 셸의 프로세스 트리를 동기로 끝내고(`closeAll({ killTrees: true })`, `재시작` 으로 끝날 때 세션 보관 프로세스의 셸은 아래 항목처럼 남긴다) 메시지 MCP 공유 연결 파일을 한 줄로 바꿔 둔다(`pauseExternalBridge`, 다음 시작이 다시 씀). 정리가 끝나면 다운로드한 설치 프로그램을 `autoUpdater.install`로 조용히 실행한다. 재시작 버튼으로 종료했을 때 설치 프로그램이 앱을 다시 띄운다. 설치 폴더의 `ezShell.exe` 를 메시지 MCP 로 쓰는 에이전트가 살아 있거나 MCP 를 다시 띄우면, 옛 제거 프로그램이 파일을 옮기지 못해 "Failed to uninstall old application files: 2" 로 실패했다 (`docs/fix/2026-11-24-update-uninstall-failed-2.md`). 알림의 `재시작` 은 먼저 `lib/updateInstall.ts` 를 거친다: 저장 안 한 서버 파일 편집 창이 있으면 설치하지 않고 알리고(그 창은 스스로 닫히지 않아 재시작이 멈춘다), 진행 중 전송이 있으면 확인받고(`update-busy-work`), 열린 탭을 기록한다(`restore-tabs-save`). 다시 시작한 뒤 첫 잠금 해제에서 `restore-tabs-take` 가 기록을 한 번 돌려주고 지우며, 본 영역 위에 `업데이트 전에 열려 있던 탭 N개를 다시 열까요?` 안내 줄(`Restore/RestoreTabsBanner.tsx`)이 뜬다. `다시 열기` 는 탭을 하나씩 다시 접속한다 (`lib/restoreTabsRun.ts`: 저장 세션 탭은 이름·칸 배치·SFTP 폴더·주 터미널의 `cd` 한 번, 로컬 터미널, 계정을 저장한 DB 탭, 분리했던 터미널 창은 본창 탭으로, 화면 좌우 나누기). 빠른 연결은 다시 열지 않고 계정이 채워진 연결 창을 칩으로 준다. 설계: `docs/plan/2026-11-18-restore-tabs-after-update.md`.
- 이전 제거 프로그램이 재시도 끝에 코드 2를 반환하면 설치 프로그램이 실행된 계정의 `%TEMP%\ezShell-install-error-<pid>-<tick>.log`에 구버전 설치 경로와 파일 접근 검사 결과를 남긴다 (`scripts/windows-update-diagnostics.nsh`). 검사에서 `Win32 32`는 공유 위반이고 `5`는 접근 거부다. 검사 시점에 잠금이 풀렸다면 실패 시각의 원인은 이 로그로 특정할 수 없다.
- 업데이트하는 동안 로컬 셸 유지 (Windows, `src/sessionHost/`): 로컬 셸은 앱 안이 아니라 **세션 보관 프로세스**(`host.js`)가 가진다. 앱은 이름 있는 파이프로 붙고(`client.js`, 토큰은 `userData/session-host.json`), `localShell.js` 는 node-pty 와 같은 모양의 `spawn` 을 받아 그대로 쓴다. `재시작`으로 창이 모두 닫히면 보관 프로세스에 keep(3분)을 보낸다. 응답을 확인한 뒤 `localShells.handOver()`로 셸 정보를 넘기고 연결을 놓는다. 창 닫기가 취소되면 keep 요청도 설치도 시작되지 않는다. 설치 프로그램이 띄운 새 앱은 잠금 해제 전에 다시 붙어 같은 id 로 셸을 되살리고(`localShells.adopt`), 첫 잠금 해제 뒤 창이 업데이트 전에 넘겨 둔 칸 배치(`local-shell-keep-layout`/`kept-layout`)로 탭을 다시 붙인다 (`lib/localShellAdopt.ts`). 복원 기록의 로컬 탭은 `shellId` 를 갖고, 되살아난 셸의 탭은 안내 줄이 다시 열지 않는다. 보관 프로세스는 keep 을 받은 뒤에만 다음 앱을 받는다. 앞 앱이 아직 붙어 있는데 다른 앱이 토큰으로 붙으면 `busy` 로 거절하고, 거절된 앱은 자기 보관 프로세스를 새로 띄운다. `npm run dev` 는 설치본과 같은 `userData` 를 쓰므로 상태 파일을 `session-host-dev.json` 으로 따로 둔다 (같은 파일을 쓰면 dev 가 설치본의 셸을 모두 빼앗고, dev 를 끄면 그 셸이 모두 끝났다: `docs/fix/2026-11-27-dev-run-took-installed-shells.md`). 앱이 업데이트가 아닌 이유로 끝나거나(강제 종료 포함) 3분 안에 새 앱이 붙지 않으면 보관 프로세스가 셸 트리를 모두 끝내고 나간다. 보관 프로세스를 띄우기 전에 연 셸(첫 실행의 복사 중), 개발 서버 실행(`openDevelopmentTask`)은 앱 안에서 열려 지금처럼 끝난다. 화면 테스트 `local-keep-through-update` (알림의 `재시작` 버튼으로 실제 순서를 거치고, 새 앱은 보관 프로세스를 5초 늦게 찾는다: 시험용 `EZSHELL_TEST_SESSION_HOST_DELAY_MS`, 시험용 재시작 모드에서는 업데이트 확인이 곧바로 다운로드 완료를 알린다). 설계: `docs/plan/2026-11-26-sessions-survive-update.md`.
  - 런타임 복사본(`runtimeCopy.js`): 보관 프로세스와 에이전트 도우미는 `%LOCALAPPDATA%\ezShell Sessions` 의 복사본으로 뜬다. `runtime-<electron>-<node-pty>-<arch>`(exe 를 `ezShell-sessions.exe` 로, Node 로 도는 데 필요한 파일 4개, node-pty)와 `app-<내용 해시>`(`host.js`, `out/main/agent-runtime`)로 나뉜다. 14일 넘게 쓰지 않은 옛 폴더만 지운다 (업데이트 전에 뜬 에이전트의 환경 변수가 옛 경로를 가리킨다).
  - 바꾸면 안 되는 것: 설치 프로그램(app-builder-lib `allowOnlyOneInstallerInstance.nsh`)은 경로가 설치 폴더 문자열로 **시작하는** 프로세스를 모두 끝내고, PowerShell 이 없으면 이름 `ezShell.exe` 로 끝낸다. 그래서 복사본 exe 는 다른 이름이고, 복사본 경로가 설치 폴더 문자열로 시작하면(대소문자 무시, 구분자 없이 비교) 보관 프로세스를 쓰지 않는다. 보관 프로세스가 설치 폴더의 파일(`app.asar` 포함)을 열어 두면 설치가 "Failed to uninstall old application files: 2" 로 실패한다.
  - 바꾸면 안 되는 것: `host.js` 는 Node 내장 모듈과 넘겨받은 node-pty 폴더만 쓴다 (복사본에 그 파일만 있다). 셸에 넘기는 환경에서 `EZSHELL_SESSIONS_*` 와 `ELECTRON_RUN_AS_NODE` 를 지운다.
  - 바꾸면 안 되는 것: `handOver()` 는 셸 정보에 시작 폴더(`launchDirectory`)와 화면이 보고한 폴더(`reportedDirectory`)를 따로 넣고, 확인된 시작 폴더(`launchIdentity`, dev·ino 는 문자열)도 함께 넣는다. `adopt()` 는 그 경로의 dev·ino 를 다시 재서 같을 때만 `launchIdentity` 를 되살린다. Windows 에서 실행 구성 도구(`run_*`)의 권한 폴더는 이 값에서만 나오므로(`runAuthorityDirectory`, `docs/architecture/local-project-run.md`), 빠지면 업데이트 뒤 에이전트의 `run_*` 가 모두 거부되고, 화면이 보고한 폴더를 시작 폴더 자리에 넣으면 권한이 없는 폴더가 권한을 얻는다.
  - 바꾸면 안 되는 것: `local-shell-list`·`local-shell-kept-layout` 은 보관 프로세스 재연결(`startSessionHost`)이 끝나기를 최대 15초 기다린 뒤 답한다. 자동 잠금 해제처럼 창이 먼저 열리면 빈 목록을 받고 배치를 소비해, 되살아난 셸이 탭으로 돌아오지 않고 복원 안내 줄이 같은 탭을 새로 열었다 (세션이 두 개씩, 채팅이 터미널로. `docs/fix/2026-11-26-kept-shells-after-update.md`).
  - 바꾸면 안 되는 것: 인계 기록으로 되살린 에이전트는 보관 프로세스가 그 셸을 되살렸을 때만 남는다. 보관 프로세스의 시작이 끝나면 `restoreAgentHandoff` 가 `agentMessages.retireLostShells(keptShellIds)` 를 부르고, 셸이 돌아오지 않았고 MCP 도 연결되지 않은 에이전트를 셸 없이 끝낸다. 이 정리가 없으면 새 셸 번호가 다시 `local:1` 부터 매겨져, 옛 에이전트가 같은 번호의 새 탭에 칩으로 한 번 더 보였다 (`docs/fix/2026-11-27-ghost-agents-after-update.md`). 셸 넘기기와 인계 기록 쓰기는 보관 프로세스가 keep에 답했을 때만 한다(`finishSessionQuit`의 `keepShells`).
  - 바꾸면 안 되는 것: `adopt()` 는 에이전트 셸의 메시지 깨우기 화면(`agentInboxWake`)에 보관 프로세스가 넘긴 출력(`backlog`)을 먼저 그린다. 그 화면은 비어서 시작하고 쉬는 CLI 는 아무것도 그리지 않아, 채팅 보내기가 "입력칸을 찾지 못했습니다"로 실패했다(터미널을 한 번 보면 크기 조정으로 다시 그려져 풀렸다).
  - 시험용 앱 중 main 의 `pty.spawn` 을 바꿔 끼우는 것(`e2e/support/localAgentApp.js`, `agentHistoryApp.js`, `antigravityChatApp.js`)은 `EZSHELL_TEST_NO_SESSION_HOST=1` 로 보관 프로세스를 끈다. `EZSHELL_TEST_UPDATE_RESTART=1`(패키징되지 않은 앱만)은 `install-update` 를 설치 없이 같은 순서로 끝내게 한다.
- 일반 종료 때도 본창의 탭을 기록한다. 사용 중에는 화면과 main이 변경을 모아 마스터 비밀번호로 암호화하고 `restore-tabs.json`을 원자적으로 바꾼다. 잠그기 직전과 Windows `query-session-end`·`session-end`에서는 받은 최신 기록을 바로 저장한다. 강제 종료 뒤에는 마지막으로 저장된 탭을 복원할 수 있다. 같은 프로세스에서 화면만 다시 불러올 때는 현재 기록을 소비하지 않으며, 업데이트 설치용 기록이 우선한다. 화면 시험 `local-restore-checkpoint`. 구현은 `docs/fix/2026-11-25-restore-tabs-on-windows-restart.md`에 있다.
- 로컬 탭의 에이전트 대화 (`lib/restoreAgents.ts`): 기록의 로컬 탭은 칸마다 그 셸에서 돌던 Claude Code·Codex (`agents: [{ pane, agent, sessionId? }]`)를 갖고, 다시 열 때 주 칸은 `claude --resume <id>` / `codex resume <id>` 로 열리고 다른 칸은 셸을 열 때 이어서 연다 (`localPaneShells.queuePaneStart`). 이어 갈 대화가 없는 에이전트(말을 건 적이 없어 Codex 기록 파일이 없거나, 기록을 찾지 못함)는 같은 종류를 새로 띄우고, 그것도 안 되면 일반 셸이다. 에이전트 종류는 사용량 보고가 없어도 메시지 목록(셸 → 종류, `agentKindsByShell`)에서 얻는다. 세션 id 는 사용량 보고에서 온다 (Claude 상태 줄의 `session_id`, Codex 는 감시기가 찾은 기록 파일의 id: 첫 응답 전에도 보고). 바꾸면 안 되는 것: 창은 세션 id 를 직접 실행하게 하지 않고 대화 기록 키(`claude:<id>`)를 `local-shell-open` 의 `resume` 으로 보낸다. main 이 대화 기록에서 다시 찾은 폴더·세션만 쓰고(앱을 막 다시 띄운 뒤라 목록이 비었으면 한 번 읽는다), 찾지 못하면 그 칸은 일반 셸로 연다. 작업 도중이던 명령은 이어지지 않고 대화가 이어진다. 채팅 보기였던 칸은 기록에 `chat: true` 가 붙고, 다시 열면 그 칸의 셸에 에이전트가 다시 묶이는 순간 채팅 보기로 연다 (`lib/pendingChatViews.ts`, 2분 안에 에이전트가 오지 않으면 터미널로 둔다). 화면 테스트 `local-restore-agents`.
- 기록(`src/restoreTabs.js`, `userData/restore-tabs.json`)은 마스터 비밀번호로 암호화하고 한 번 읽으면 지운다. 업데이트용 기록은 24시간 뒤 만료된다. 비밀번호와 화면 내용은 기록에서 제외한다 (`lib/restoreTabs.ts` 의 `buildRestoreRecord`). 돌아온 기록은 화면이 다시 검사한다 (`readRestoreRecord`: 칸 id 형식·중복, 경로의 제어 문자). 사용자가 다시 열기를 선택하면 접속한다. `cd` 는 `cdCommand` 로만 만든다 (작은따옴표, `~` 는 밖, 줄바꿈이 든 경로는 보내지 않음). 본창의 위치·크기·최대화 여부는 `userData/window-state.json` 에 따로 저장한다 (`src/windowState.js`, 저장된 위치가 지금 연결된 화면에 보이지 않으면 기본 위치).
