# 업데이트 뒤 같은 에이전트가 탭마다 둘씩 보이던 문제

## 증상

2026-11-27 2.40.0 으로 업데이트한 뒤, 사이드바 로컬 작업 트리의 탭마다 에이전트 칩이 실제보다 많이 보였다. 예를 들어 mbris-new 의 backend 탭과 frontend 탭에 Claude 칩이 둘씩 보였다. 그런데 메시지 MCP 의 `list_agents` 와 OS 프로세스 목록에는 Claude 6개, Codex 4개만 있어서 수가 서로 맞았다.

## 원인

업데이트 때 이전 앱은 에이전트 인계 기록(`agent-handoff.json`)을 남긴다. 새 앱은 잠금 해제 뒤 `importHandoff` 로 이 기록을 읽어 이전 에이전트를 `active: true` 그대로 되살린다. 이 동작은 세션 보관 프로세스가 그 셸을 실제로 되살렸다고 전제한다.

이번에는 그 전제가 깨졌다.

- 에이전트 연결 폴더 `ezshell-agent-d2M0KI` 는 이전 앱이 10:38 에 만든 폴더이고, 새 앱도 이 폴더를 그대로 썼다. 따라서 인계 기록은 적용됐다.
- 반면 보관 프로세스 `ezShell-sessions.exe` 는 13:13 에 새 앱이 새로 띄운 것이었다. 따라서 셸은 하나도 이어지지 않았다.
- 셸이 없으니 탭 복원이 셸을 새로 열었고, 에이전트도 `--resume` 으로 새로 등록됐다.

되살아난 옛 에이전트는 CLI 가 없어서 MCP 로 다시 붙지 못했고, 끝났다는 신호도 받지 못해 계속 `active` 로 남았다. 또 넘겨받은 셸이 없으면 새 셸 번호는 다시 `local:1` 부터 매겨진다(`localShell.js` 의 `nextId`). 그래서 옛 에이전트의 셸 ID 와 새 셸의 ID 가 겹쳤다. 사이드바 칩(`LocalSessionAgents`)은 셸 ID 로 탭을 찾기 때문에, 옛 에이전트가 같은 번호의 새 탭에 한 번 더 그려졌다. `list_agents` 는 연결된 에이전트만 보여 주기 때문에 이 문제가 드러나지 않았다.

보관 프로세스가 왜 새로 떴는지(keep 실패, 설치 프로그램의 종료, `busy` 거절 중 무엇인지)는 남은 기록이 없어 확인하지 못했다. 그 원인과 상관없이, 셸이 돌아오지 않은 에이전트를 정리하지 않는 것이 이번 문제의 직접 원인이다.

## 수정

- `agentMessages.retireLostShells(keptShellIds)` 를 새로 만들었다. 인계 기록으로 되살린 에이전트 가운데 셸 ID 가 있는 에이전트만 대상으로 한다. 그 셸이 이번에 되살린 셸 목록에 없고 MCP 도 연결되지 않았으면 그 에이전트를 끝낸다.
  - 메시지가 남은 에이전트는 기록으로 남긴다. 이때 `shellId: ''`, `active: false`, `status: 'ended'` 로 두어 새 탭에 붙지 않게 한다. 메시지가 없는 에이전트는 지운다(`archiveExternal` 과 같은 규칙).
  - 그 에이전트의 인계 토큰, 재연결 자격 증명, 돌아오지 않은 셸의 인계 셸 토큰도 함께 지운다.
- `main.js` 의 `startSessionHost` 는 되살린 셸 ID 를 `keptShellIds` 에 적는다. `restoreAgentHandoff` 는 인계 기록을 적용한 뒤, 보관 프로세스의 시작이 끝나기를 기다렸다가 `retireLostShells` 를 부른다. 창이 쓰는 15초 대기가 아니라 시작 전체를 기다린다. 그래야 늦게 되살아난 셸의 에이전트를 잘못 끝내지 않는다.

- 원인 쪽도 막았다. codex-29 가 짚은 대로, `beforeUpdateRestart` 는 `sessionHost.keep()` 이 `false` 를 돌려줘도 그 결과를 버렸다. `will-quit` 은 `sessionHost.ready()` 만 보고 셸을 넘기고 인계 기록을 썼다. 그래서 보관 프로세스가 keep 을 받지 못하면, 셸은 앱과 함께 끝나는데 에이전트 인계 기록은 남았다. 이제 모든 창이 닫힌 뒤 keep 응답을 확인하고, 보관에 성공했을 때만 셸을 넘기고 인계 기록을 쓴다(`finishSessionQuit`의 `keepShells`). keep 이 실패하면 예전처럼 셸 트리를 끝내고, 다음 앱에서 에이전트가 새로 등록된다.
- 이렇게 막아도, 인계 기록을 쓴 뒤 설치가 실패하거나(NSIS 오류 2) 사용자가 작업 관리자에서 보관 프로세스까지 끄면 기록이 남는다. 이 경우는 위의 `retireLostShells` 가 정리한다.

## 검증

- `src/ipc/agentHandoff.test.js` 에 시험 2개를 더했다.
  - 셸이 돌아오지 않은 에이전트는 셸 없이 끝나고, 인계 토큰이 더는 받아들여지지 않는다.
  - 메시지가 없는 에이전트는 지워지고, 되살아난 셸의 에이전트와 이 앱이 직접 띄운 에이전트는 그대로 남는다.
- `npx vitest related src/ipc/agentMessages.js --run` 은 128개 통과, 1개 건너뜀이었다.
- 화면 시험 `local-keep-through-update` 는 ALL PASSED 였다. 이 시험은 셸이 업데이트를 거쳐 이어지는 경로를 확인한다. keep 응답 확인을 더한 뒤에도 다시 돌려 통과했다.
- 화면 시험 `local-update-lost-host`는 별도 프로필에서 업데이트 재시작 뒤 보관 프로세스를 종료하고 남은 인계 기록으로 복원한다. 같은 대화 재개, 이전 메시지 보존, 새 에이전트 칩 하나를 확인한다. 이전 에이전트 정리를 빼면 같은 셸에 칩 둘이 그려져 시험이 실패한다.

## 남은 것

- 지금 떠 있는 2.40.0 의 유령 칩은 이 수정이 들어간 다음 버전으로 업데이트하거나 앱을 다시 켤 때 사라진다. 다시 켜면 인계 기록이 없으므로 에이전트가 모두 새로 등록된다.
- 보관 프로세스가 업데이트를 넘기지 못한 원인은 따로 확인해야 한다. 지금은 보관 프로세스 쪽에 그 이유를 남기는 기록이 없다.
