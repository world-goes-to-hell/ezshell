# 채팅 보내기가 "입력칸에 글이 그대로 들어가지 않아 보내지 않았습니다" 로 자주 막힘

2026-11-23 사용자 보고 (채팅을 자주 보내는 사용자): 채팅 보기에서 보낸 글이 `not-drawn` 으로 자꾸 막힌다.

## 원인
`agentInboxWake.submitText` 는 괄호 붙여넣기 뒤 headless xterm 으로 입력칸을 읽어, 1.5초 안에 원문과 글자까지 같아야만 Enter 를 보냈다. 실제 CLI(Claude Code 2.1.330, Codex 0.171.0, Windows ConPTY)로 재현한 결과, 같아질 수 없는 경우가 여럿이었다.

- 낱말 단위 줄바꿈: 입력칸 줄 수를 글자 수로 어림해서(`maxInputRows`), 긴 낱말이 많은 글은 프롬프트 줄을 찾지 못했다 (80열 367자가 8줄, 예산 6줄).
- CLI 가 글자를 바꿔 그림: Claude 는 `👋🏽→👋`, `👨‍👩‍👧‍👦→👨`, `🇰🇷→🇰`, `café→café`. Codex 는 ✅·❤️·ZWJ·결합 악센트를 빼고 그린다 (일부는 받은 본문에서도 빠진다: CLI 쪽 동작).
- 낮은 칸: Claude 는 입력칸을 스크롤해 `─── ↑ N more ───` 를 그리고 끝부분만, Codex 는 `↑` 를 붙여 일부만 보여 준다.
- 앞 Enter 직후 입력칸이 늦게 비워져 다음 전송이 `composer-not-empty`.
- Codex 긴 붙여넣기 표시(`[Pasted Content N chars]`)가 1.5초 넘게 늦게, 또는 앞 글자와 함께(`al[Pasted …]`) 그려짐.
- 실패하면 붙인 글이 입력칸에 남아 다음 전송도 "쓰던 글이 있습니다" 로 막혔다.

Orca(MIT)의 같은 기능(`native-chat-paste-landed.ts`)은 일치를 Enter 시점을 고르는 데만 쓰고, 5초가 지나면 Enter 를 보낸다. 처음 만들 때 붙여넣기 → 따로 Enter 순서만 옮기고 일치를 관문으로 만든 것이 차이였다.

## 수정
- 붙인 뒤 500ms 부터 입력칸을 읽는다. 원문(또는 붙여넣기 표시)이 보이고 100ms 뒤에도 같으면, 다르게 그려졌으면 입력칸이 바뀐 뒤 300ms 그대로면 Enter 를 한 번 보낸다. 5초가 되면 붙인 글이 입력칸에 나타났을 때만 보낸다 (빈 칸·흐린 제안이면 실패: Claude 는 대기열이 있을 때 빈 입력칸 Enter 로 대기열을 보낸다).
- Enter 직전에 같은 에이전트(프로세스)·입력칸·대상, 확인 질문 없음, 사용자 입력 없음을 다시 본다. 셸 프롬프트로 보이는 행이 있으면 보내지 않는다.
- 입력칸은 화면 전체에서 찾고, 낮은 Claude 칸은 `↑/↓ N more` 구분선이나 아래 구분선+바닥줄로 인정한다. 진행 표시(스피너)는 입력칸 밖이라 판정에 쓰지 않는다 (작업 중에는 화면 전체가 200ms 멎는 일이 없었다).
- 같은 셸의 전송은 줄을 세운다. Enter 를 보낸 글이 아직 입력칸에 있으면 비워질 때까지 기다리고, Enter 를 못 보낸 앱의 글은 전체가 일치할 때만 지운다.
- Enter 는 한 번뿐이다. 제출됐는지는 대화 기록으로 확인해 안 들어갔으면 `전송 확인 안 됨`·`다시 보내기` 를 보인다 (CLAUDE.md "Agent Chat View" 의 전송 확인).
- 흐린 안내(`Try "…"`)는 셀이 흐린지만 보고 판단한다 (터미널에서 쳤다 지운 뒤 쓰던 글로 잘못 봤다). ConPTY 가 꽉 찬 행 마지막 칸에 커서를 둘 때 결합 문자 셀도 끝으로 본다.
