# 영역 캡처 `바로작업`이 일부 에이전트에게 "입력칸을 찾지 못했습니다"로 실패

2026-11-23 사용자 보고: `Ctrl+Alt+Shift` 캡처의 `바로작업`을 오래 쉰 에이전트에게 보내면, 에이전트의 입력칸을 찾지 못했다며 보내지 못했다.

## 조사
- 그 문구는 `agentInboxWake.submitText` 의 `no-composer` 다. 캡처 보내기도 채팅 보내기와 같은 `chatSend` → `submitText` 를 쓴다.
- 오래 쉼 자체는 원인이 아니었다. 실제 Claude CLI(70×30)를 node-pty 와 가상 화면에 붙여 12분 동안 두었는데, 30초마다 본 입력칸은 계속 `empty` 였다. 창 포커스를 잃은 뒤(`ESC[O`)에도 같았다.
- 쉰 지 10분 뒤의 메모리 비우기(`EmptyWorkingSet`)도 원인이 아니었다. 비운 뒤 포커스를 바꿔 25ms 마다 보았는데, 입력칸을 한 번도 놓치지 않았다. 다시 그리는 출력도 40바이트뿐이었다.

## 원인
- 입력칸 판정(`composer()`)은 가상 화면이 괄호 붙여넣기 모드(`ESC[?2004h`)일 때만 입력칸을 찾는다. 붙여넣기로 글을 넣기 때문에 지우면 안 되는 조건이다.
- CLI 는 이 모드를 시작할 때 한 번만 켠다.
- 셸에 직접 입력해 띄운 에이전트(사용자의 에이전트는 모두 이렇다)는 메시지 MCP 가 붙는 순간(`localShell.attachExternalAgent`) 가상 화면을 새로 만든다. 이때 그 셸의 최근 출력(`backlog`, 256~512KB)만 다시 넣는다.
- MCP 가 늦게 붙거나 출력이 많아서 시작 부분이 `backlog` 밖으로 밀려났으면, 새 화면은 그 모드를 끝내 모른다. 그러면 그 에이전트에게는 채팅·캡처·메시지 알림이 모두 입력칸을 찾지 못한다.
  - MCP 가 늦게 붙는 경우: 시작할 때 연결에 실패했다가 나중에 붙는다. 이 세션도 처음에는 메시지 MCP 연결에 실패했다가 나중에 붙었다.
  - 출력이 많은 경우: 잠든 에이전트를 `--resume` 으로 깨워 긴 대화가 다시 찍힌다.

## 수정 (`src/localShell.js`)
- 셸마다 출력 전체에서 터미널 모드 두 가지를 기억한다: 괄호 붙여넣기(`2004`)와 응용 커서 키(`1`). 함수는 `trackTerminalModes` 이고, 조각 사이에 걸린 시퀀스를 위해 뒤 16자를 남긴다.
- 가상 화면을 만들 때 `backlog` 뒤에 그 모드를 다시 넣는다(`modeSequences`). 둘 다 화면에 아무것도 그리지 않는 시퀀스라 화면 내용은 그대로다. `backlog` 뒤에 넣으므로 결과는 지금 상태와 같다.
- 화면을 바꾸는 모드(대체 화면 `1049` 등)는 넣지 않는다. 화면을 지운다.

## 확인
- 단위 테스트 `localShell.test.js` 의 "reads the composer of a CLI whose start scrolled out of the backlog…": 고치기 전 코드에서는 `null`, 고친 뒤에는 `empty` 인 것을 확인했다.
- 실제 앱에서 실패했던 에이전트의 화면은 보지 못했다. 위 경로가 그 에이전트에 일어났는지는 확인하지 못했다.
