# 외부 단축키로 작업 개요 열기

다른 프로그램에서 `Ctrl+Alt+Space`를 누르면 대상 모니터의 작업 개요가 늦게 열렸다. Windows에서 모니터 5대 중 주 모니터와 위쪽 모니터를 사용해, 임시 프로필의 개발 앱과 별도 프로세스 창으로 측정했다. 각 버전에서 같은 모니터 조합을 9번 열었다.

측정은 테스트 도우미에서 마지막 수정키를 뗀 뒤와 같은 지점에 호출을 넣는 방식으로 시작했다. 실제 도우미의 창 앞으로 가져오기부터 신호, main·renderer 왕복, 캡처, 창 이동, 개요 표시까지 실행했다. 첫 표시는 개요가 DOM에 들어온 뒤 두 번째 `requestAnimationFrame`으로 잡았다.

## 원인

기존에는 `desktopCapturer.getSources`가 여러 모니터의 썸네일을 준비한 뒤 창을 옮겼다. 본 측정에서 캡처 완료까지 중앙값은 675ms였고, 창 이동 시작부터 `enter-full-screen`까지는 9ms였다. 별도 측정에서는 `getSources`가 Promise를 돌려주기 전부터 main이 587ms와 752ms 동안 막혔다. 120ms 타이머도 그 호출이 끝날 때까지 실행되지 않았다. [Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer/)

## 수정

- 외부 단축키는 개요의 어두운 흐림 배경을 사용한다. 창이 대상 모니터로 이동한 뒤 별도 이미지가 들어와 배경을 바꾸는 단계가 없다. 앱 안에서 단축키를 누르면 현재 모니터를 캡처하는 기존 배경을 쓴다.
- main이 만든 요청 번호로 외부 단축키와 renderer의 열기 요청을 연결한다. 같은 본창의 주 프레임에서 3초 안에 한 번만 쓸 수 있다. 닫거나 잠그면 대기 요청을 지운다.
- 외부 프로그램의 모니터 선택, 창의 원래 위치·크기와 최대화 상태 복원은 기존 창 처리 경로를 사용한다. 단축키 도우미의 수정키 뗌·포커스 처리도 기존 경로를 따랐다.

## 전후 측정

| 구간 | 수정 전 중앙값 | 수정 후 중앙값 |
| --- | ---: | ---: |
| 수정키 해제 지점 → main의 `overview` 수신 | 19ms | 17ms |
| `overview` 수신 → `work-overview-show` 도착 | 2ms | 16ms |
| 캡처 호출 → 썸네일 준비 | 675ms | 생략 |
| 창 이동 시작 → `enter-full-screen` | 9ms | 8ms |
| `enter-full-screen` → 개요 첫 표시 | 12ms | 9ms |
| 수정키 해제 지점 → 개요 첫 표시 | 720ms | 51ms |

총 시간 범위는 674~863ms에서 48~65ms로 줄었다. 수정 후 9번 모두 대상 모니터에 개요가 표시됐고, 닫자 원래 창 위치와 크기가 돌아왔다.

## 검증

- 관련 단위 테스트 9개 통과. 외부 요청의 캡처 생략, 대상 모니터, 최대화 복원과 만료·취소·중복 요청을 확인했다.
- `npm run typecheck`와 `npm run build` 통과.
- Windows `local-work-overview` 화면 검사 25개 통과. 첫 실행에서 마우스를 올렸을 때 미리보기가 열리지 않았고, 같은 빌드로 재실행했을 때는 열렸다.
