# MCP 백그라운드 작업 도구 설계

- 날짜: 2026-10-02
- 구분: 보안 경계 (Claude 가 서버에서 30초를 넘는 명령을 실행한다)
- 상태: 구현·보안 검토 반영·검증 완료 (2026-10-02), 설치본 반영 대기

## 목적
`run_command` 는 30초가 지나면 명령을 중단한다. 빌드, 패키지 설치, 테스트, 큰 로그 검색처럼 30초를 넘는 명령은 지금 실행할 수 없다.
시간이 오래 걸리는 명령을 **작업(job)** 으로 시작하고, Claude 가 나중에 출력과 종료 상태를 읽어 가게 한다. 사용자는 MCP 활동 패널에서 진행 상황을 보고 언제든 중지할 수 있다.

## 방식 선택
| 방식 | 내용 | 판단 |
|---|---|---|
| **A. 앱이 채널을 붙잡는다 (채택)** | main 프로세스가 SSH 실행 채널을 요청과 분리해 유지하고, 출력을 메모리에 모은다 | 기존 원칙(출력은 메모리에만, 잠그면 모두 멈춤, 활동 패널에서 중지)을 그대로 지킨다. 서버에 아무것도 남기지 않는다 |
| B. 서버에 `nohup` 으로 띄우고 로그 파일을 읽는다 | 앱을 닫아도 계속 실행된다 | 출력(비밀이 섞일 수 있음)이 서버 디스크에 남고, 앱을 잠가도 멈추지 않으며, PID 로 죽일 때 다른 프로세스를 죽일 위험이 있다 |
| C. `run_command` 의 제한 시간만 늘린다 | 구현이 가장 작다 | 요청 하나가 몇 분 동안 열려 있어야 하고, 그동안 같은 세션의 다른 명령이 모두 기다린다 |

A 를 택하면 **앱을 잠그거나 닫으면 작업도 끝난다.** 이것은 제약이지만 의도한 성질이다 (잠금 = Claude 의 작업이 모두 멈춤).

## 도구 인터페이스
```
run_command { session, command, background?, timeout_minutes? }   (기존 도구에 인자 2개 추가)
job_output  { job, wait_seconds? }
stop_job    { job }
list_jobs   { }
```
- `background: true` 면 작업을 시작하고 작업 ID(`job-` + 무작위 8자)를 바로 돌려준다. `timeout_minutes` 는 1~60, 기본 10. `background` 없이 주면 오류.
- `job_output`: 지난번에 읽은 뒤로 새로 나온 출력과 상태(실행 중/완료/시간 초과/중지/실패/출력 한도 초과), 종료 코드, 경과 시간을 돌려준다. 작업이 실행 중이면 **끝나기를** `wait_seconds`(0~25, 기본 10)까지 기다린 뒤 그동안의 출력을 모아서 준다 (구현 중 바뀜: 처음에는 새 출력이 나오면 바로 돌려줬는데, 43초 작업에 41번 호출됐다). 한 번에 64KB 까지. 읽지 못한 사이에 밀려난 출력이 있으면 그 크기를 알린다.
- `stop_job`: 중지를 요청하고 마지막 상태를 돌려준다. 이미 끝난 작업이면 그 상태를 그대로 돌려준다.
- `list_jobs`: 허용된 세션의 작업(ID, 세션 표시 이름, 명령, 상태, 경과 시간) 목록. Claude 가 작업 ID 를 잊었을 때 쓴다.
- stdout 과 stderr 는 도착한 순서대로 한 줄기로 합쳐서 준다 (나눠 읽으려면 위치를 두 개 관리해야 한다).
- 결과에는 기존과 같이 세션 표시 이름만 넣고 주소·계정은 넣지 않는다.

## 처리 순서
1. **시작** (`run_command` + `background`): 기존 `guarded` 경로를 그대로 지난다 (잠금, `mcpEnabled`, 명령 판정, 절대 차단, 감사 로그 시작 기록, 필요하면 확인 창, 허용 뒤 재확인, 작업 디렉터리 일치 확인).
   - 판정 규칙(위험도)은 바꾸지 않는다. 다만 백그라운드 작업은 알림 수준과 무관하게 **항상 확인 창**을 띄운다 (보안 검토 M3 반영. 처음 설계는 낮음 명령을 확인 없이 시작할 수 있게 했다).
   - 확인 창에는 "백그라운드 실행 · 최대 N분" 을 함께 보여 준다.
   - 동시 실행 한도(세션당 3개, 전체 6개)를 넘으면 확인 창을 띄우기 전에 거부한다.
2. **실행**: 세션의 대기열 안에서 연결과 작업 디렉터리를 확인하고 채널을 연 뒤, 대기열을 놓아준다. 작업은 대기열 밖에서 계속 실행되므로 같은 세션의 다른 명령·파일 도구가 기다리지 않는다. stdin 은 기존처럼 닫는다.
3. **출력**: 제어 문자를 제거하고 작업별 메모리 버퍼(마지막 1MB)에 넣는다. 같은 내용을 활동 패널에도 실시간으로 보낸다. 디스크에는 쓰지 않는다.
4. **끝**: 종료, 제한 시간 초과, 중지(Claude 의 `stop_job`, 사용자의 "중지" 버튼), 연결 끊김, 출력 16MB 초과 가운데 먼저 일어난 것으로 끝난다. 이때 감사 로그 끝 기록과 활동 패널의 최종 상태를 남긴다.
5. **읽기/중지/목록**: 잠금 해제 상태이고 그 작업의 세션이 지금도 `mcpEnabled` 일 때만 응답한다. 확인 창은 없다 (이미 판정·승인된 명령의 출력이다).

## 중지가 실제로 멈추게 하기
PTY 없이 실행하므로 채널을 닫는 것만으로는 서버의 프로세스가 죽지 않는다. OpenSSH 7.9 미만(CentOS 7 의 7.4 등)은 시그널 요청도 무시한다. 30초짜리 명령에서는 감수했지만 몇십 분짜리 작업에서는 감수할 수 없다.
- 작업 명령 앞에 셸 PID 를 stderr 첫 줄로 내보내는 한 줄을 붙이고, 그 줄은 출력에서 걷어 낸다. sshd 는 PTY 없는 실행을 새 세션으로 띄우므로 이 PID 가 프로세스 그룹 ID 다.
- 중지·시간 초과 때: 시그널 요청(KILL) → 채널 닫기 → 같은 연결의 새 채널로 `kill -KILL -- -<PID>`. 작업이 아직 끝나지 않았을 때만 보낸다.
- PID 줄을 받기 전에 중지되면 시그널 요청만 먼저 보내고, PID 줄이 오기를 최대 1초 기다린 뒤에 채널을 닫는다 (먼저 닫으면 PID 줄이 끊겨 kill 을 보낼 수 없다).
- 작업이 끝났다는 보고는 kill 명령이 끝난 뒤에 한다. 잠글 때는 작업이 끝나는 대로 연결을 닫기 때문이다.
- 연결이 끊겨서 끝난 경우에는 죽일 방법이 없다. 결과에 "서버에서 계속 실행 중일 수 있음" 이라고 적는다. 중지했지만 서버가 끝을 알려 주지 않았고 PID 도 얻지 못한 경우에도 같은 주의를 붙인다.

## 연결 수명
- 실행 중인 작업이 있는 연결은 유휴 5분이 지나도 닫지 않는다.
- **잠금·MCP 끄기·앱 종료**: 모든 작업에 중지를 보내고 작업 목록과 출력을 즉시 지운다. 연결은 새 요청이 쓰지 못하게 바로 떼어 내되, 중지 명령이 서버에 도착하도록 작업이 끝나거나 3.5초가 지난 뒤에 닫는다. 앱 종료는 작업이 있을 때 이 과정이 끝날 때까지 기다린다 (`main.js` 의 `before-quit`).
- 작업은 채널을 요청하는 순간부터 그 연결의 작업으로 센다. 채널이 열리는 도중에 연결을 떼어 내도 작업을 중지할 수 있어야 하기 때문이다.
- **세션 저장**(지금은 모든 연결을 닫는다): 저장 뒤 `mcpEnabled` 가 아니게 된 세션의 작업은 중지한다. 나머지 작업은 계속 실행한다. 작업이 있는 연결은 떼어 내서(새 요청은 새 설정으로 새로 접속) 작업이 끝나면 닫는다. 세션 목록을 읽지 못하면 모든 작업을 중지한다.

## 제한값
| 항목 | 값 |
|---|---|
| 실행 시간 | 기본 10분, 최대 60분 |
| 동시 실행 | 세션당 3개, 전체 6개 (OpenSSH 기본 `MaxSessions` 10 안쪽) |
| 작업당 보관 출력 | 마지막 1MB |
| 작업당 총 출력 | 16MB 를 넘으면 중지 (`yes` 같은 명령이 main 프로세스를 붙잡지 않게) |
| 한 번에 읽는 출력 | 64KB |
| 끝난 작업 보관 | 최근 20개, 잠금·종료 때까지 |
| 활동 패널의 요청당 출력 | 마지막 512KB (넘으면 앞에서부터 버림), 조각 2,000개 (넘으면 오래된 조각을 합침) |
| 출력 전달 | 50ms 마다 묶어서, 묶음당 조각 64개까지 |

## 감사 로그와 활동 패널
- 감사 로그: 시작 기록에 `background: true` 와 제한 시간(분), 끝 기록에 종료 코드·시간 초과·취소 여부. `job_output`, `list_jobs` 는 기록하지 않는다 (명령이 아니다). 출력은 기록하지 않는다.
- 활동 패널: 작업은 끝날 때까지 "실행 중" 항목으로 남고 "백그라운드" 표시가 붙는다. 터미널 보기에 출력이 실시간으로 이어지고, 기존 "중지" 버튼이 작업을 중지한다.

## 바꾸는 파일
| 파일 | 내용 |
|---|---|
| `src/mcp/jobStore.js` (새) | 작업 목록, 출력 버퍼와 읽은 위치, 기다렸다 읽기, 한도, 보관 개수, 전체 지우기 |
| `src/mcp/jobChannel.js` (새) | 채널 하나에서 작업 실행: PID 줄 걷어 내기, 시간 제한, 출력 한도, 중지 순서 |
| `src/mcp/jobTools.js` (새) | `job_output`, `stop_job`, `list_jobs` 핸들러 |
| `src/mcp/sessionGateway.js` | `startJob`, 작업이 있는 연결의 유휴 유지, 연결 떼어 내기(`retire`) |
| `src/mcp/tools.js` | `guarded` 에 백그라운드 경로 (끝 기록을 작업이 끝날 때로 미룸) |
| `src/mcp/server.js` | 도구 등록, 인자, 설명 |
| `src/mcp/controller.js` | 작업 저장소 생성, 잠금·세션 저장·종료 때 처리 |
| `src/mcp/activityLog.js`, `src/renderer/lib/mcpActivity.ts` | 요청당 출력 512KB 제한 |
| `McpApprovalDialog.tsx`, `McpActivityPanel.tsx`, `McpActivityTerminal.tsx`, `types/index.ts` | 확인 창의 백그라운드 표시, 활동 항목의 "백그라운드" 표시 |
| `CLAUDE.md` | MCP 절에 작업 도구와 바꾸면 안 되는 것 |

주요 인터페이스:
```
gateway.startJob(session, command, { signal, expectedCwd, limitMs, onOutput })
  → Promise<{ cwd, stop(), done: Promise<{ exitCode, signal, timedOut, cancelled, dropped, overflow }> }>
gateway.retireAll({ graceMs })            // 떼어 내고, 작업이 끝나거나 graceMs 뒤에 닫음
jobStore.create(fields, { stop }) → id | { error }
jobStore.append(id, text) / finish(id, result)
jobStore.read(id, { waitMs, signal }) → Promise<{ job, text, skippedBytes }>
jobStore.stop(id) / stopWhere(predicate) / list() / clear()
```

## 테스트 목록
권한·비노출·취소 경로는 구현보다 먼저 쓴다.
- `jobStore`: 읽은 위치가 이어짐, 1MB 를 넘으면 앞이 밀리고 밀린 크기를 알림, 64KB 씩 나눠 읽기, 기다리는 중 출력·종료·취소로 깨어남, 세션당·전체 한도, 끝난 작업 20개 보관, `clear` 뒤 기다리던 읽기가 끝남
- `jobChannel` / `sessionGateway` (테스트용 ssh2 서버): 대기열을 막지 않음(작업 실행 중 다른 명령이 바로 실행됨), PID 줄이 출력에 섞이지 않음, 시간 초과·중지 때 KILL 요청과 `kill` 명령이 감, 이미 끝난 작업에는 `kill` 을 보내지 않음, 출력 16MB 초과 중지, 연결 끊김, 작업 중 유휴 타이머로 닫히지 않음, `retire` 뒤 새 요청은 새 연결을 씀
- `tools` / `jobTools`: 잠긴 상태에서 모든 작업 도구 거부, 절대 차단 명령은 백그라운드로도 차단, 확인 거부·만료·취소 때 작업이 생기지 않음, 한도 초과는 확인 창 없이 거부, 허용이 꺼진 세션의 작업은 읽기·목록에서 빠지고 중지됨, 감사 로그의 시작·끝 기록, 결과에 주소·계정 없음, `background` 없는 `timeout_minutes` 는 오류
- `controller`: 잠금 때 작업 중지·목록 삭제, 세션 저장 때 허용이 꺼진 세션의 작업만 중지, 세션 목록을 못 읽으면 모두 중지
- `activityLog`, `mcpActivity.ts`: 512KB 를 넘으면 앞에서부터 버림

## 보안 검토 반영 (2026-10-02)
CRITICAL 없음. 승인 우회, 잠금 뒤 출력 누출, PID 를 통한 명령 주입은 발견되지 않았다.

| 지적 | 반영 |
|---|---|
| H1 한두 바이트씩, 또는 stdout·stderr 를 번갈아 내는 출력이 이벤트마다 보관 버퍼 전체를 복사하게 해 main 과 창이 멈춤 | 출력을 50ms 마다 묶어서 넘김(`jobChannel.js`). 작업 버퍼는 한도의 2배가 쌓였을 때만 자름. 활동 출력의 자르기를 한 번 훑는 방식으로 바꾸고 조각 수를 2,000개로 제한 (main, 렌더러 모두). 실측: 6,000줄에 이벤트 64번 |
| M1 PID 를 알기 전에 중지되면(채널이 열리는 도중의 잠금·중지 포함) 구버전 서버에 프로세스가 남고, 결과에는 "중지됨" 만 나옴 | 채널 요청 시점부터 작업으로 세어 연결을 유지. PID 줄을 기다린 뒤에 채널을 닫음. 끝을 확인하지 못한 중지에는 "계속 실행 중일 수 있음" 주의를 붙임 |
| M2 앱 종료가 kill 명령의 도착을 기다리지 않음 | 작업이 있으면 종료를 잠시 미루고 `shutdown()` 이 끝난 뒤 종료 |
| M3 낮음 판정 명령(`tail -f`, `find /` 등)이 확인 없이 최대 60분 실행됨 | 백그라운드 작업은 알림 수준과 무관하게 항상 확인 창 |
| L3 잠근 뒤에도 창의 메모리에 활동 출력이 남음 | 활동 구독이 끝날 때(잠금 화면으로 바뀔 때) 창의 목록을 비움 |
| L1 세션의 호스트·계정을 바꿔도 실행 중인 작업은 옛 연결에서 계속됨 | 그대로 둠. 사용자가 승인한 서버에서 승인한 명령이 도는 것이고, 새 요청은 새 설정으로 접속한다 |
| L2 진행 중 항목이 목록 상한을 넘겨 쌓임 | 해당 없음. 진행 중 항목만으로 100개를 넘으면 자른다 (`capItems` 의 마지막 `slice`) |

## 검증 결과 (2026-10-02)
- 전체 테스트 1,501개 통과, typecheck 통과, build 성공.
- 실제 OpenSSH 9.6 (WSL 에서 일반 사용자로 띄운 sshd, `docs/brain/2026-10-02-real-sshd-in-wsl-for-verification.md`) 에 게이트웨이를 직접 붙여 24개 항목 통과:
  실행 셸이 pid = pgid = sid 임, 출력이 실행 중에 도착함, 중지·시간 초과·출력 한도 뒤에 프로세스가 남지 않음.
  시그널 요청을 무시하는 서버를 흉내 낸 상태에서도 중지, 시간 초과, 잠금(연결 떼어 내기), 채널이 열리자마자 중지, 채널이 열리는 도중의 잠금 뒤에 프로세스가 남지 않음.
  대조: 채널과 연결을 닫기만 하면 `sleep` 이 서버에 남는다.
- 실제 앱(같은 서버): 40초짜리 명령을 작업으로 실행해 `job_output` 3번으로 끝까지 읽음(모든 줄이 정확히 한 번), 확인 창에 "백그라운드 실행 · 최대 N분" 표시, 활동 패널의 "백그라운드" 표시와 실시간 출력, 작업 실행 중 다른 명령 실행,
  활동 패널의 중지·`stop_job`·잠금·앱 종료 뒤에 서버에 프로세스가 없음, 잠금 뒤 작업 목록과 창의 활동 기록이 지워짐, 감사 로그에 시작·끝 기록이 있고 출력은 없음.
- 확인하지 못한 것: 실제 구버전 서버(OpenSSH 7.9 미만). 시그널 요청을 무시하는 동작은 클라이언트 쪽에서 흉내 냈다.
