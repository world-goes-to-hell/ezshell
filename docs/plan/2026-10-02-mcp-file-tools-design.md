# MCP 파일 쓰기 도구 설계

- 날짜: 2026-10-02
- 구분: 보안 경계 (Claude 가 서버의 파일 내용을 바꾼다)
- 상태: 구현·보안 검토 반영·검증 완료, 설치본 반영 대기

## 목적
Claude Code 가 서버의 텍스트 파일을 만들거나 고칠 때, 사용자가 **바뀌는 내용을 그대로 보고** 허용하게 한다.

지금은 파일을 고치려면 `run_command` 로 히어닥이나 `sed -i` 를 보내야 한다. 그러면
- 확인 창에 긴 셸 명령이 그대로 보여서 무엇이 바뀌는지 읽어 내기 어렵고,
- 따옴표·변수 치환 때문에 의도와 다른 내용이 써질 수 있고,
- 확인 창을 본 시점과 실행 시점 사이에 파일이 바뀌어도 알 수 없다.

## 범위
| 도구 | 하는 일 |
|---|---|
| `write_file` | 새 파일을 만들거나 파일 전체를 새 내용으로 바꾼다 |
| `edit_file` | 파일 안의 문자열 한 곳(또는 `replace_all` 이면 전부)을 바꾼다 |

넣지 않는 것과 이유:
- `read_file`: 읽기는 `run_command` 의 `cat`, `sed -n '100,200p'` 로 이미 된다. 필요해지면 이 설계의 SFTP 통로 위에 추가한다.
- 폴더 만들기, 삭제, 이름 바꾸기, 권한 변경: `run_command` + 확인 창으로 한다.
- `sudo` 로 올려 쓰기: 접속 계정의 권한으로만 쓴다.
- 256KB 를 넘는 파일, 텍스트(UTF-8)가 아닌 파일: 거부한다.

## 도구 인터페이스
```
write_file { session, path, content }
edit_file  { session, path, old_string, new_string, replace_all? }
```
- `path`: 절대 경로, `~/...`, 또는 세션의 현재 작업 디렉터리 기준 상대 경로. 1024자 이하.
- `content`: 256KB 이하. `old_string` 은 1자 이상.
- 결과(성공): 세션 표시 이름, 실제 경로, 새 파일/수정, 추가·삭제 줄 수, 크기.
- 결과(실패): 이유 한 줄. 서버의 주소·계정은 넣지 않는다.

## 처리 순서
1. **세션 확인**: 잠금 해제 상태, `mcpEnabled` 세션 (기존 `guarded` 와 같음).
2. **경로 정하기**: `~` 와 상대 경로를 풀고 `..` 를 정리한다. NUL 문자, 빈 경로, `/` 로 끝나는 경로는 거부.
3. **대상 조사** (SFTP):
   - 부모 폴더의 실제 경로(`realpath`)를 구한다. 부모 폴더가 없으면 거부.
   - 대상이 심볼릭 링크면 가리키는 실제 파일을 대상으로 삼는다 (요청 경로와 실제 경로를 둘 다 기억).
   - 폴더·장치·소켓 등 일반 파일이 아니면 거부.
   - 있으면 크기를 먼저 보고(256KB 초과 거부) 내용을 읽는다. UTF-8 이 아니거나 NUL 이 있으면 거부.
4. **새 내용 만들기**:
   - `write_file`: 받은 내용.
   - `edit_file`: `old_string` 이 정확히 한 번 나와야 한다 (`replace_all` 이면 한 번 이상). 없거나 여러 번이면 사용자에게 묻지 않고 오류.
   - 결과가 지금 내용과 같으면 "변경 없음" 으로 끝낸다 (확인 창 없음).
5. **판정**: 쓰기는 항상 `위험`. 알림 수준 설정과 무관하게 확인 창을 띄운다. 이유에 다음을 붙인다.
   - 새 파일 만들기 / 기존 파일 덮어쓰기
   - 비밀 정보가 있을 수 있는 경로 (기존 `SENSITIVE_PATHS`, 요청 경로와 실제 경로 모두 검사)
   - 심볼릭 링크를 따라 다른 파일에 씀
6. **확인 창**: 세션, 실제 경로(다르면 요청 경로도), 새 파일/수정, 추가·삭제 줄 수, **변경 내용 전체(diff)**, 이유. 제한 시간은 180초 (명령은 60초. diff 는 읽는 데 시간이 든다).
7. **허용 뒤 다시 확인**: 잠금·취소·세션 설정 변경을 다시 본다 (기존과 같음). 그리고 파일을 다시 읽어 확인 창에 보여 준 "이전 내용"과 같은지 본다. 다르면(없던 파일이 생긴 경우 포함) 쓰지 않고 "파일이 바뀌어 쓰지 않았습니다" 로 끝낸다.
8. **쓰기** (보안 검토 뒤 바뀜: 아래 "보안 검토 반영"의 M-4 참고. 지금은 자르지 않고 열어 같은 핸들로 비교하고 쓴다):
   - 기존 파일: 같은 파일에 덮어쓴다. 임시 파일을 만들어 바꿔치기하지 않는다.
   - 새 파일: 이미 있으면 실패하는 방식으로 연다. 권한 0644.
   - 쓴 뒤 크기를 확인한다.
   - 쓰는 도중 실패하면 기억해 둔 이전 내용으로 되돌리기를 시도하고, 되돌렸는지 여부를 결과에 적는다.
   - 쓰기가 시작된 뒤에 온 취소는 쓰기를 끝낸 뒤에 반영한다 (반쯤 쓴 파일을 남기지 않는다).

### 결정과 이유
| 결정 | 이유 |
|---|---|
| 셸을 거치지 않고 SFTP 로 읽고 쓴다 | 따옴표·변수 치환·줄바꿈으로 내용이 달라질 여지가 없다 |
| 덮어쓰기는 같은 파일에 한다 (임시 파일 + 바꿔치기 아님) | 바꿔치기는 원자적이지만 소유자·권한·ACL·SELinux 표지·하드 링크가 달라진다. 서버 설정 파일에서는 이쪽 피해가 더 크다. 256KB 이하라 쓰는 시간이 짧고, 실패하면 이전 내용으로 되돌린다 |
| 쓰기는 알림 수준과 무관하게 항상 확인 | "위험만 확인" 이 기본값이고 쓰기는 위험이므로 결과는 같지만, 설정을 바꿔도 쓰기 확인은 끌 수 없게 한다 |
| 확인 창에 diff 전체를 보여 준다 (줄이지 않음) | 보지 못한 부분을 허용하게 되면 확인의 의미가 없다. 크기 제한이 있어 전체를 보여 줄 수 있다 |
| 허용 뒤 파일이 바뀌었으면 쓰지 않는다 | 사용자가 허용한 것은 "그 내용에서 이 내용으로" 다. `run_command` 의 작업 디렉터리 묶기와 같은 원칙 |
| 실제 경로 기준으로 판정하고 보여 준다 | `notes.txt` 라는 링크가 `/etc/sudoers` 를 가리킬 수 있다 |
| 줄바꿈·인코딩을 바꾸지 않는다 | CRLF 파일에 LF 조각을 찾으면 "찾지 못함" 이 된다. 오류 문구에 그 가능성을 적는다 |
| 세션별 설정을 새로 만들지 않는다 | 쓰기는 확인을 거친 명령과 같은 권한이다. `mcpEnabled` 로 충분하다 |

### 기록
- 감사 로그: 도구 이름과 경로(`write_file /etc/app.conf`), 판정, 결과만. **내용과 diff 는 기록하지 않는다.**
- MCP 활동 패널: 요청 한 건으로 보인다. diff 는 명령 출력처럼 메모리에만 두고 잠금 때 지운다.

## 지켜야 할 조건과 테스트 (이 목록을 먼저 테스트로 쓴다)
**확인 없이 쓰지 않는다**
- 알림 수준이 `danger`/`medium`/`all` 어느 것이어도 확인 창을 거친다
- 거부·만료·취소·확인 중 잠금 → SFTP 쓰기 호출이 없다
- 허용 뒤 세션의 `mcpEnabled` 가 꺼졌으면 쓰지 않는다

**보여 준 것과 쓰는 것이 같다**
- 확인 창에 넘어간 경로·이전 내용·새 내용과 실제 쓰기 인자가 같다
- 허용 뒤 파일 내용이 달라졌으면 쓰지 않는다 / 없던 파일이 생겼으면 쓰지 않는다 / 있던 파일이 사라졌으면 쓰지 않는다
- 심볼릭 링크: 확인 창과 쓰기가 모두 실제 경로를 쓴다. 민감 경로 이유가 실제 경로 기준으로 붙는다

**거부해야 하는 입력** (확인 창을 띄우지 않고 오류)
- 빈 경로, NUL 포함, `/` 로 끝남, 1024자 초과, 부모 폴더 없음
- 폴더·장치·소켓, 256KB 초과, UTF-8 아님
- `edit_file`: 찾는 문자열 없음, 여러 번 나오는데 `replace_all` 아님, 결과가 256KB 초과
- 변경 없음은 오류가 아니고 확인 창도 없다

**경로 처리**
- `~`, `~/x`, 상대 경로(작업 디렉터리 기준), `a/../b`, `//`, 공백·한글·작은따옴표가 든 경로
- `..` 로 루트 위로 나가려는 경로는 `/` 에서 멈춘다

**실패 처리**
- 쓰는 도중 실패 → 이전 내용으로 되돌리기 시도, 결과에 되돌림 여부
- 쓰기 시작 전 취소 → 쓰지 않음. 쓰기 시작 뒤 취소 → 끝까지 쓰고 결과에 적음
- SFTP 를 열 수 없는 서버 → 이유를 알리고 끝 (연결과 명령 실행에는 영향 없음)
- 제한 시간(30초)을 넘으면 중단

**밖으로 나가면 안 되는 것**
- 감사 로그에 내용·diff 가 없다
- Claude 에게 가는 결과와 오류에 호스트 주소·계정이 없다 (세션 이름은 기존 `exposedName`)
- 잠금 뒤 활동 목록에 diff 가 남지 않는다

**기존 동작 유지**
- 파일 작업이 같은 세션의 명령과 섞이지 않고 순서대로 실행된다
- 파일 도구가 추가되어도 `run_command`, `cd` 의 테스트가 그대로 통과한다

화면(확인 창의 diff 표시)은 typecheck 와 실제 앱 확인 1회로 본다. 끝난 뒤 보안 검토 1회.

## 보안 검토 반영
검토 결과: 확인 창을 거치지 않고 쓰이는 경로는 없음. CRITICAL 없음, HIGH 1, MEDIUM 8, LOW 9.

| 지적 | 반영 |
|---|---|
| H-1 diff 계산이 줄 수의 제곱으로 느려져 main 프로세스가 멈춤 (실측: 16,000줄에 30초) | 계산에 300ms 제한. 넘으면 "파일 전체를 지우고 새로 씀"으로 표시(여전히 전체가 보임). 줄 수 10,000 초과는 거부 |
| M-1 확인 없이 내용을 추정할 수 있음 ("찾지 못함", "N번 나옴", "변경 없음") | 그 파일을 `cat` 으로 읽을 때 확인이 필요한 알림 수준이면 `edit_file` 을 거부하고, "변경 없음" 도 확인 창을 거친 뒤에만 알린다. 알림 수준을 읽지 못하면 막는 쪽으로 처리 |
| M-2 시간 제한이 쓰는 도중 채널을 닫아 파일이 잘림 | 쓰기를 시작할 때 제한을 120초로 늘린다(`beginWrite`). 쓴 뒤 크기 확인, close 실패도 쓰기 실패로 처리 |
| M-3 `replace_all` 결과가 수백 MB 로 부풂 | 결과 크기를 먼저 계산해 넘으면 만들지 않고 거부 |
| M-4 재확인과 열기 사이에 경로가 링크로 바뀌면 따라감 | 파일을 자르지 않고 한 번 열어(`r+`), 그 핸들의 내용을 보여 준 내용과 비교하고, 같은 핸들에 쓴 뒤 길이를 맞춘다. 경로가 바뀌어도 따라가지 않는다 |
| M-5 크기 0 으로 보이는 파일을 끝없이 읽음 | 핸들에서 256KB+1 바이트까지만 읽는다 |
| M-6 `/proc`, `/sys` 의 파일을 막지 않음 (명령 정책과 불일치) | `/proc`, `/sys`, `/dev` 는 요청 경로와 실제 경로 모두에서 거부. 열기 전에 판정 |
| M-7 확인 창 표시 문제 | 숨은 문자 목록 보강(한글 채움 문자, 공백처럼 보이는 문자 등). 경로의 줄바꿈·탭·앞뒤 공백 표시. 긴 줄은 줄바꿈. 변경 내용을 끝까지 내려 본 뒤에만 허용. 창이 뜬 뒤 0.8초는 허용 버튼 비활성 |
| M-8 확인 창이 초당 4번 diff 전체를 다시 그림 | 계산 결과와 diff 표시를 메모이즈 |
| L-1 새 비밀 파일이 644 | 비밀 경로의 새 파일은 600, 확인 창 이유에 표시 |
| L-2 로그인·부팅 때 실행되는 파일에 경고 없음 | `.bashrc`, cron, systemd, sshd 설정 등에 이유를 붙임 |
| L-3 감사 로그에서 승인 여부를 구별할 수 없음 | `approved: true` 와 쓴 내용의 SHA-256(내용 자체는 아님)을 기록 |
| L-5 서버가 닫은 SFTP 채널을 다시 씀 | 채널의 close/end 에서 잊는다 |

반영하지 않은 것:
- L-7 승인 대기열에 상한이 없다. 요청을 많이 보내면 사용자가 하나씩 거부해야 한다 (활동 패널의 "중지"로도 끝낼 수 있음).
- L-6 시간 제한으로 버려진 작업은 채널이 닫힌 뒤 스스로 끝날 때까지 메모리에 남는다.
- M-1 의 나머지: 파일이 있는지, 텍스트인지, 256KB 를 넘는지는 확인 없이 알려진다 (내용이 아니라 속성).
- M-2 의 나머지: 쓰는 도중 다른 세션을 저장하면 연결이 모두 닫힌다(`onSessionsSaved`). 창이 매우 짧다.

## 열어 둔 한계 (검토 반영 뒤)
- `edit_file` 은 알림 수준이 "모든 명령 확인"이면 쓸 수 없고, "중간 이상 확인"이면 비밀 경로에서 쓸 수 없다. 그때는 `run_command` 로 읽고 `write_file` 로 쓴다.
- 10,000줄을 넘는 파일은 다룰 수 없다.
- 바뀐 곳이 많은 변경은 "전체 교체"로 보여서 어디가 바뀌었는지 한눈에 보이지 않는다 (내용은 전부 보인다).

## 실제 앱에서 확인한 것
- 새 파일: 확인 창에 실제 경로, "새 파일", 추가 줄 전체. 허용 전에는 서버에 아무것도 쓰이지 않는다. 허용하면 내용 그대로, 권한 644.
- 수정: 바뀐 줄과 주변 줄. 같은 파일에 덮어써서 권한(640)이 유지된다.
- 거부하면 파일이 그대로다.
- 심볼릭 링크: 실제 경로와 요청 경로가 함께 보이고, 이유에 링크와 비밀 경로가 붙는다.
- 확인 창이 열려 있는 동안 파일이 바뀌면 허용해도 쓰지 않는다.
- 숨은 문자는 `⟨U+202E⟩` 처럼 드러나고 경고가 뜬다. CRLF 줄 끝은 `␍` 로 표시하고 경고하지 않는다.
- 변경 없음, 폴더, FIFO, 없는 상위 폴더는 확인 창 없이 끝난다.
- 3,000줄 변경도 전체가 확인 창에 들어가고 스크롤된다 (표시까지 약 0.8초).
- 명령 확인 창은 그대로다 (60초, 명령 표시).
- MCP 활동의 터미널 보기에 쓰기 요청과 변경 내용이 보인다. 감사 로그 파일에는 도구와 경로만 있다.

## 열어 둔 한계
- 덮어쓰기는 원자적이지 않다. 쓰는 순간 연결이 끊기고 되돌리기도 실패하면 파일이 잘린 채 남을 수 있다 (결과에 알림).
- 접속 계정에 쓰기 권한이 없으면 실패한다. `sudo` 가 필요한 파일은 `run_command` 로 해야 한다.
- 새 파일의 권한은 0644 고정이다. 실행 파일로 만들려면 `chmod` 를 따로 실행한다.
