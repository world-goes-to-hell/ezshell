# 여러 저장소 작업과 기동 순서 (2026-11-26)

시안: `mockups/multi-repo-workspace.html` (장면 번호는 이 시안의 번호). 사용자 요청: MSA 처럼 한 폴더에 서비스 저장소를 모아 두고 그 폴더를 로컬 작업으로 잡는 경우를 지원하고, 서비스의 **기동 순서**를 정할 수 있어야 한다 (사용자가 특히 중요하다고 짚음).

## 규칙

로컬 작업은 사용자가 등록한 폴더 하나다. 그 안에서 찾은 git 저장소는 그 작업에 딸린 **구성원**으로 보여준다. 하위 저장소를 로컬 작업으로 따로 올리지 않는다 (사이드바가 커진다). 따로 등록한 저장소만 따로 보인다.

| 등록한 폴더 | 보이는 모양 |
|---|---|
| A. git 저장소, 아래에 저장소 없음 | 지금과 같다 |
| B. git 이 아닌 폴더, 아래에 저장소들 (MSA) | 프로젝트 줄에 공통 브랜치, 카드에 실행 구성과 접힌 "저장소 N개" |
| C. git 저장소 안에 또 저장소 (submodule·중첩) | A 처럼 보이고, 워크트리 카드에 B 와 같은 "저장소 N개" 줄 |

## 1부: 하위 저장소 (담당 개발C)

### main
- 찾기: 등록한 폴더(또는 워크트리) 아래 2단계까지, 최대 50개. `node_modules`·`build`·`target`·`dist`·`.git`·점으로 시작하는 폴더는 들어가지 않는다. 이미 있는 `findNestedRepositories`/`nestedRepositoriesOf`(`src/ipc/localProjects.js`, 작업 공간 패널이 쓴다)를 넓혀 쓰거나 같은 규칙으로 맞춘다. 두 개의 찾기 규칙을 만들지 않는다.
- 저장소마다 읽는 값: 폴더(등록한 폴더 기준 상대 경로), 브랜치(또는 분리된 HEAD), 업스트림 유무, 앞선 커밋 수(↑), 뒤처진 커밋 수(↓), 수정한 파일 수. `git status --porcelain=v2 --branch` 한 번으로 읽는다. 동시 실행은 4개로 제한한다.
- fetch: `git fetch --quiet` (프롬프트 없이: `GIT_TERMINAL_PROMPT=0`, SSH 는 `BatchMode=yes`). 창에 포커스가 올 때, 같은 프로젝트에 대해 10분에 한 번까지. 설정으로 끌 수 있다 (기본 켬, 아침 확인 항목 1).
- pull: 각 저장소의 현재 브랜치를 `git pull --ff-only` 로만 받는다. 수정한 파일이 있거나, 갈라졌거나(↑와 ↓ 모두 있음), 업스트림이 없거나, 분리된 HEAD 면 손대지 않고 이유와 함께 "건너뜀"으로 돌려준다. 병합·리베이스·충돌 처리는 하지 않는다. 모두 받기는 동시에 4개, 저장소마다 결과(받음 N / 건너뜀 이유 / 실패 메시지)를 돌려준다.
- 보안: 실행 구성 IPC(`src/ipc/runPresets.js` 의 `handle`·`resolveProject`)와 같은 경계를 쓴다. 본창 주 프레임과 잠금 해제를 확인하고, `realDirectory` 로 실제 로컬 폴더인지 본다 (`.git` 경로 거부, `isLocalFilePath` 로 UNC·장치 경로 거부). `roots.resolveRoot` 는 쓰지 않는다: 그건 작업 공간 패널의 경계(열린 셸 기준)라서, 셸을 열지 않은 등록 폴더를 막는다. 저장소 경로는 그 폴더 안의 실제 경로인지 다시 확인한다. 경로는 화면이 준 문자열을 그대로 쓰지 않고 main 이 찾은 목록 안에 있는 것만 받는다. 출력·오류 메시지는 500자로 자른다.
- 새 파일을 `main.js` 가 런타임에 `require` 하면 `electron.vite.config.ts` 의 `MAIN_RUNTIME_MODULES`/`DIRECTORIES` 규칙을 따른다 (`src/ipc/`, `src/localFiles/` 는 이미 디렉터리로 등록돼 있다).

### 화면 (장면 1·2·3·4·4′·5)
- 프로젝트 줄: 공통 브랜치(가장 많은 저장소의 브랜치)와 저장소 수, 받을 커밋이 있는 저장소 수 `↓N`. 반반이면 "브랜치 여러 개".
- 실행 구성 줄: 구성의 폴더가 어느 하위 저장소 안이면, 그 저장소가 공통 브랜치와 다를 때 브랜치 칩(주황), 받을 커밋이 있으면 `↓N` 칩(누르면 그 저장소만 받기), 수정 중이면 `수정` 칩. 모두 같으면 아무것도 붙지 않는다.
- 카드 아래 접힌 "저장소 N개" 줄. 펼치면 기본으로 "다른 것"(다른 브랜치·↑·↓·수정)만, 탭으로 "전체". 머리에 `모두 최신으로`. 진행 중에는 줄마다 받음/건너뜀/대기/돌기, 끝나면 요약 알림(건너뜀·실패 목록).
- 저장소 줄: 누르면 그 폴더에서 로컬 터미널. 우클릭: 받기, 기동(실행 구성 추가 창을 그 폴더로), 로컬 터미널, 에이전트 열기, 파일 탐색기로 열기, 따로 로컬 작업으로 올리기.
- 저장소 줄의 브랜치나 우클릭 메뉴 `브랜치 바꾸기…`를 누르면 로컬 브랜치와 마지막 fetch에서 읽은 원격 추적 브랜치를 검색할 수 있다. Enter나 더블클릭으로 선택한 브랜치로 바꾼다. 원격에만 있으면 같은 이름의 로컬 추적 브랜치를 만든다. 수정·스테이징된 파일, 진행 중인 병합·리베이스·체리픽, 덮어쓸 추적되지 않은 파일이 있으면 이유를 표시한다.
- 1차에서 빼는 것은 하위 저장소의 워크트리다.

## 2부: 기동 순서 (담당 개발D)

### 모델
- 순서는 **프로젝트에 하나**. 실행 구성 목록과 따로 `startOrder` 를 둔다: 단계의 배열, 단계마다 구성 id 목록과 "다음 단계로 넘어가는 기준".
- 기준: `ready`(지금의 "뜸": 로그에서 주소·포트를 찾음), `log`(로그에 이 문구가 나오면, 한 줄 200자 이하), `url`(헬스 URL 이 2xx: `http://127.0.0.1`·`localhost`·`[::1]` 만), `none`(기다리지 않음). 동시 단계는 단계 안의 모두가 기준을 넘어야 다음으로 간다.
- 기다리는 시간(기본 5분, 단계 공통)과 넘었을 때(멈추고 알리기 / 계속).
- 저장 형식 `version` 을 올리거나, 없는 `startOrder` 는 지금 상태에서 만든다: 지금 목록 순서대로 구성마다 한 단계, 다음 구성의 `waitReady` 가 켜져 있으면 앞 단계 기준 `ready`, 아니면 `none`. `inAll` 이 꺼진 구성은 순서에 넣지 않는다 (순서 화면의 "모두 실행에서 뺀 것" 칸).
- 구성이 지워지면 순서에서 빠지고, 새로 추가한 구성은 마지막 단계 뒤 새 단계로 들어간다.

### 실행
- 모두 실행: 단계 순서대로, 단계 안은 동시에. 기다리는 이유(포트·문구·URL)와 경과 시간을 상태로 내보낸다.
- 멈춤: 시간 초과, 앞 단계 서비스가 죽음 → 묶음 실행을 멈추고 "로그 보기 · 건너뛰고 계속 · 다시 시도".
- 모두 중지: 단계를 거꾸로.
- 하나만 실행: 앞 단계 서비스가 꺼져 있으면 "앞 단계도 함께 띄울까요?" (설정으로 끌 수 있다).
- 에이전트의 `run_*` 도구가 모두 실행을 쓰면 같은 순서를 따른다.

### 화면 (장면 6′·6″)
- 순서 화면: 단계 카드, 서비스를 끌어 단계 사이 이동, 같은 단계 = 동시, 빈 곳에 놓으면 새 단계. 단계마다 기준 선택(문구·URL 은 입력칸). 공통 옵션: 기다리는 시간과 넘었을 때, 중지 거꾸로, 하나만 실행할 때 묻기.
- 진입: 실행 구성 머리의 메뉴 "기동 순서…". 지금의 구성 위·아래 옮기기와 "모두 실행 때 앞 구성이 뜬 뒤 실행" 스위치는 이 화면으로 옮긴다.
- 실행 중: 머리에 "N/M단계"와 진행 막대, 줄 앞에 단계 번호, 기다리는 칩("문구 기다림 0:41").
- 일반 프로젝트(gsd-prj 의 백엔드 → 프론트)에도 같은 화면을 쓴다.

묶음은 띄울 구성을 고르기만 하고 순서는 2부의 기동 순서를 따른다 (장면 6). 2부의 모델이 들어간 뒤 시작한다.

## 함께 고치는 파일
- `RunPresetsSection.tsx`: 머리·진행(개발D), 줄의 저장소 칩(개발C). 칩은 별도 컴포넌트로 만들어 줄에 한 줄로 끼운다. 이 파일을 크게 고칠 때는 상대에게 먼저 알린다.
- `LocalProjectsTree.tsx`, `src/preload.js`, `src/renderer/types/index.ts`: 둘 다 더한다. 남의 줄은 고치지 않는다.

## 리뷰 뒤 정한 것 (2026-11-26 밤, 개발B)
- 하위 저장소의 `.git/config` 가 fetch 중 명령을 실행할 수 있었다 (`remote.*.uploadpack`, `core.gitProxy`, UNC remote 는 NTLM 해시 전송; git 2.45.1 에서 재현). 그래서 이렇게 막는다:
  - 프로토콜은 https·ssh·file 만 허용한다. UNC remote 는 거부한다.
  - 저장소 로컬 설정에 위험한 키(uploadpack·gitProxy·sshCommand·credential helper·gpg.program·filter 등)가 있으면 그 저장소는 자동 fetch 에서 뺀다. 직접 받기는 그 내용을 보여 주는 확인 창을 거친다.
  - 받기는 `git merge --ff-only --no-verify-signatures @{upstream}` 로 한다.
- 교차 리뷰(개발D)에서 빈틈이 더 나왔다:
  - `core.alternateRefsCommand`
  - 전역 설정의 include 가 작업 폴더 안을 가리키는 경우
  - 프록시 설정
  - 검사한 뒤 fetch 가 설정을 다시 읽는 사이의 차이
  - 위험 키 목록으로는 자동 실행을 보장할 수 없다고 보고 **신뢰 모델**로 바꿨다. 자동 fetch 는 사용자가 "믿는다"고 확인한 로컬 작업에서만 돌고, 기본은 꺼짐이다 (VS Code 의 작업 영역 신뢰와 같은 생각). 수동 fetch·받기는 사용자가 누른 것이라 터미널에서 git 을 치는 것과 같은 신뢰 수준으로 본다.
- 상태를 못 읽은 저장소(시간 초과·safe.directory·lock)는 목록에서 빼지 않고 오류를 표시한다. 앱이 `safe.directory` 를 바꾸지는 않는다.
- 찾기 규칙은 하나로 두고 깊이·개수는 옵션으로 받는다. 작업 공간 패널은 예전 한도를 유지하고, 사이드바는 2단계 50개를 쓴다.
- 기동 순서:
  - 앞 단계가 비정상 종료(오류 코드)했을 때만 멈춘다. 정상 종료와 사용자 중지는 넘어간다.
  - 묶음에 든 "모두 실행에서 뺀" 구성은 맨 뒤 단계로 붙인다.
  - 사용자가 시작한 묶음을 에이전트가 끊으려면 묶음 안의 모든 구성이 에이전트 조작을 허용해야 한다.
  - 진행 중에는 순서를 저장하지 못한다.
