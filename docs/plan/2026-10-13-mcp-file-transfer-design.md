# MCP 파일 전송 도구 설계

- 날짜: 2026-10-13
- 구분: 보안 경계 (Claude 가 내 PC 의 파일을 서버로 보내고, 서버의 파일을 내 PC 에 쓴다)
- 상태: 구현·보안 검토 반영·검증 완료 (실제 앱 화면 확인과 실제 OpenSSH 서버의 덮어쓰기 확인은 남음)

## 목적
Claude Code 가 내 PC 와 서버 사이에서 파일 하나를 올리거나 내려받게 한다. 빌드 결과물을 서버에 올리거나, 서버의 로그·덤프를 PC 로 가져오는 작업이 대상이다.

지금 있는 `write_file` 은 256KB 이하 텍스트만 다루고, 내용이 MCP 요청에 통째로 실려 온다. 바이너리나 큰 파일은 보낼 방법이 없다.

## 지금까지의 도구와 다른 점
이 도구는 처음으로 **앱이 내 PC 의 파일 시스템을 읽고 쓴다.** 새로 생기는 위험은 두 가지다.
- 올리기: 서버 출력에 섞인 지시에 속은 Claude 가 PC 의 비밀 파일(개인 키, 토큰)을 서버로 보낼 수 있다. 바이너리는 확인 창에서 내용을 읽어 볼 수 없다.
- 내려받기: 서버가 정한 내용이 PC 의 임의 위치(시작 프로그램 폴더, 설정 파일)에 쓰일 수 있다. Claude Code 자체의 파일 쓰기 권한 확인을 거치지 않는 경로가 된다.

그래서 PC 쪽은 **사용자가 미리 등록한 폴더 안에서만** 읽고 쓰고, 전송마다 항상 확인 창을 띄운다.

## 범위
| 도구 | 하는 일 |
|---|---|
| `upload_file` | PC 의 파일 하나를 서버에 올린다 |
| `download_file` | 서버의 파일 하나를 PC 에 내려받는다 |

넣지 않는 것과 이유:
- 폴더 통째 전송: 확인 창에서 무엇이 오가는지 한눈에 볼 수 없다. 필요하면 `tar` 로 묶은 뒤 파일 하나로 보낸다.
- 1GB 를 넘는 파일, 일반 파일이 아닌 것(장치, 소켓, FIFO).
- `sudo` 로 올려 쓰기: 접속 계정의 권한으로만 쓴다.
- 내려받은 파일 열기·실행: 하지 않는다.

## 도구 인터페이스
```
upload_file   { session, local_path, remote_path, overwrite? }
download_file { session, remote_path, local_path, overwrite? }
```
- `local_path`: 절대 경로만. 등록된 전송 폴더 안이어야 한다.
- `remote_path`: `write_file` 과 같은 규칙 (절대 경로, `~/...`, 작업 디렉터리 기준 상대 경로. 1024자 이하).
- `overwrite`: 기본 false. 받는 쪽에 파일이 이미 있으면 확인 창을 띄우지 않고 오류로 끝낸다. true 여도 확인 창에 "덮어쓰기" 를 표시한다.
- 결과: 20초 안에 끝나면 세션 표시 이름, 양쪽 실제 경로, 크기, SHA-256. 끝나지 않으면 작업 ID 를 돌려주고 기존 `job_output` / `stop_job` / `list_jobs` 로 진행을 보고 멈춘다.
- 실패: 이유 한 줄. 서버의 주소·계정은 넣지 않는다.

## PC 쪽 접근 범위
- 설정 > MCP 에 "파일 전송 허용 폴더" 목록을 둔다. **기본은 비어 있고, 비어 있으면 두 도구 모두 거부한다** (등록 방법을 안내하는 오류).
- 폴더는 main 프로세스의 폴더 선택 창으로만 추가한다. 렌더러나 Claude 가 경로 문자열을 넘겨 추가할 수 없다 (`clientSetup` 과 같은 방식). 최대 10개, `mcp.json` 에 저장.
- 앱의 사용자 데이터 폴더(세션, 마스터 비밀번호, MCP 토큰)를 포함하는 폴더는 등록할 수 없다. 그러면 드라이브 C 의 루트, 홈 폴더, AppData 도 함께 막힌다.
- 경로 검사 순서: ① 글자만 보고 등록 폴더 밖이면 파일 시스템을 건드리지 않고 거부 → ② 실제 경로(심볼릭 링크·정션을 푼 경로)를 구해 다시 등록 폴더 안인지 확인 → ③ 사용자 데이터 폴더 안이면 거부.
- 거부하는 경로 형태: UNC(`\\서버\...`), 장치 경로(`\\?\`, `\\.\`), 대체 데이터 스트림(`파일:스트림`), 예약 이름(`CON`, `NUL` 등), 끝이 점이나 공백인 이름.
- 등록 폴더 밖의 경로는 있든 없든 같은 오류를 낸다 (파일이 있는지 알려 주지 않는다).

## 처리 순서
1. **세션 확인**: 잠금 해제 상태, `mcpEnabled` 세션 (기존과 같음).
2. **PC 경로 검사**: 위 "PC 쪽 접근 범위".
3. **양쪽 조사**
   - 보내는 쪽 파일을 **한 번 열고 그 핸들로** 종류·크기·수정 시각을 본다. 일반 파일이 아니거나 1GB 를 넘으면 거부.
   - 받는 쪽: 부모 폴더가 있어야 한다. 서버 경로는 실제 경로를 구하고 `/proc`, `/sys`, `/dev` 를 거부한다 (`write_file` 과 같음). PC 의 받는 파일이 링크·정션이면 거부한다.
   - 받는 쪽에 파일이 있는데 `overwrite` 가 아니면 오류.
4. **판정**: 항상 `위험`. 알림 수준과 무관하게 확인 창을 띄운다. 이유에 붙이는 것:
   - 방향 (PC → 서버 / 서버 → PC), 새 파일 / 덮어쓰기
   - 서버의 비밀 경로 (기존 `SENSITIVE_PATHS`. 내려받기에서는 "비밀 파일을 PC 로 가져옴")
   - PC 의 비밀로 보이는 파일 (`.ssh`, `.env`, `*.pem`, `*.key`, `id_rsa` 등. 올리기에서는 "비밀일 수 있는 파일을 서버로 보냄")
   - 내려받는 파일이 실행·스크립트 확장자 (`.exe`, `.dll`, `.bat`, `.cmd`, `.ps1`, `.vbs`, `.js`, `.lnk`, `.msi` 등)
   - 서버에서 심볼릭 링크를 따라 다른 파일에 씀 / 덮어쓰면 소유자가 접속 계정으로 바뀜
5. **확인 창**: 방향, 세션, PC 실제 경로, 서버 실제 경로(요청 경로와 다르면 둘 다), 크기, 새 파일/덮어쓰기, 이유. 제한 시간 60초. 기존처럼 창이 뜬 뒤 0.8초는 허용 버튼이 눌리지 않는다.
6. **허용 뒤 다시 확인**: 잠금·취소·세션 허용 여부. 보내는 파일의 크기·수정 시각이 확인 창에 보여 준 값과 같은지 본다. 다르면 보내지 않는다.
7. **전송**
   - 받는 쪽에는 임시 파일에 쓴다 (같은 폴더의 `.<이름>.ezshell-part-<난수>`, 이미 있으면 실패하는 방식으로 연다. 서버에서는 권한 600).
   - 보내는 쪽은 3 에서 연 핸들에서 읽는다. 경로를 다시 열지 않는다. 읽으면서 SHA-256 을 계산한다.
   - 다 쓴 뒤 크기를 확인하고, 보내는 파일의 크기·수정 시각을 한 번 더 본다. 전송 중에 바뀌었으면 실패로 처리한다.
   - 받는 쪽 원래 파일이 확인 창 시점과 같은 상태(없었으면 지금도 없음, 있었으면 크기·수정 시각이 같음)일 때만 임시 파일을 제 이름으로 바꾼다. 서버에서는 기존 파일의 권한을 임시 파일에 맞춘 뒤 바꾼다 (새 파일은 644, 비밀 경로는 600).
   - 실패·취소·잠금이면 임시 파일을 지우고, 받는 쪽 원래 파일은 건드리지 않는다.
8. **진행 표시**: MCP 활동 패널에 전송량을 1초에 한 번 표시한다. 패널의 "중지" 와 `stop_job` 으로 멈춘다.

### 결정과 이유
| 결정 | 이유 |
|---|---|
| PC 쪽은 등록한 폴더 안에서만, 기본은 빈 목록 | 차단 목록은 빠뜨리는 경로가 생긴다. 허용 목록은 사용자가 고른 범위 밖으로 나갈 수 없다. 켜지 않은 사람에게는 기능이 없는 것과 같다 |
| 전송마다 항상 확인 | 폴더를 등록했다는 것이 그 안의 모든 파일을 보내도 된다는 뜻은 아니다. 바이너리는 내용을 보여 줄 수 없으므로 경로·크기·방향이라도 매번 본다 |
| 임시 파일에 쓰고 이름 바꾸기 (`write_file` 은 같은 파일에 덮어쓰기) | 전송은 몇 분이 걸릴 수 있고 1GB 의 이전 내용을 기억해 둘 수 없다. 같은 파일에 쓰다 끊기면 되돌릴 방법이 없다. 대신 서버의 소유자·ACL·하드 링크가 달라질 수 있어서, 소유자가 바뀌는 경우는 확인 창에 알린다 |
| 보내는 파일은 한 번 연 핸들에서만 읽는다 | 확인한 뒤에 경로가 다른 파일(링크)로 바뀌어도 따라가지 않는다 (`write_file` 의 M-4 와 같은 원칙) |
| 오래 걸리는 전송은 기존 작업(job)으로 등록 | 요청 하나는 30초 안에 끝난다는 기존 구조를 유지한다. 작업 개수 제한(세션당 3개·전체 6개), 잠금·MCP 끄기·세션 허용 해제 때의 중지를 그대로 물려받는다 |
| 전송은 명령 대기열과 별도의 SFTP 채널을 쓴다 | 대기열 안에서 하면 전송이 끝날 때까지 그 세션의 `run_command` 가 멈춘다 |
| `overwrite` 를 명시해야 덮어쓴다 | 이름이 겹친 것을 모르고 덮어쓰는 실수를 줄인다. 확인 창이 마지막 방어선 하나만 되지 않게 한다 |
| 세션별 설정을 새로 만들지 않는다 | 서버 쪽 권한은 확인을 거친 `write_file` 과 같다. `mcpEnabled` 로 충분하고, 새로 필요한 제한은 PC 쪽 폴더다 |

## 모듈
| 파일 | 책임 |
|---|---|
| `src/mcp/localPath.js` (새) | PC 경로의 형태 검사, 등록 폴더 안인지 판정. 실제 경로를 구하는 함수는 주입받는다 |
| `src/mcp/localFile.js` (새) | PC 파일을 핸들로 열어 조사·읽기, 임시 파일 쓰기와 이름 바꾸기, 정리. `fs` 는 주입받는다 |
| `src/mcp/remoteTransfer.js` (새) | SFTP 로 서버 파일 조사, 핸들 읽기, 임시 파일 쓰기와 이름 바꾸기, 정리 |
| `src/mcp/transferPolicy.js` (새) | 판정과 이유 (비밀 경로, 실행 확장자, 덮어쓰기, 링크, 소유자 변경) |
| `src/mcp/transferTools.js` (새) | 두 도구의 처리 흐름. 잠금·감사·활동·취소는 `toolShared.js` 를 같이 쓴다 |
| `src/mcp/sessionGateway.js` | `startTransfer(session, { signal, limitMs }, task)`: 대기열과 분리된 SFTP 채널을 열어 넘기고, 그 연결의 작업으로 센다 |
| `src/mcp/mcpConfig.js` | `transferRoots` 와 `addTransferRoot` / `removeTransferRoot`. 렌더러가 보내는 일반 설정 변경(`update`)으로는 바꿀 수 없다 |
| `src/mcp/ipc.js` | `mcp-add-transfer-folder`(main 이 선택 창을 연다), `mcp-remove-transfer-folder` |
| `src/mcp/server.js`, `tools.js`, `controller.js` | 도구 2개 등록과 조립 |
| `McpApprovalDialog.tsx`, `mcpLabels.ts`, `types/index.ts` | 전송 요청의 확인 창 표시와 문구 |
| 설정 > MCP 탭 | 전송 허용 폴더 목록 (추가·삭제) |

새 의존성은 없다.

### 기록
- 감사 로그: 도구 이름, 방향, PC 경로, 서버 경로, 크기, 승인 여부, SHA-256. **파일 내용은 기록하지 않는다.**
- MCP 활동 패널: 요청 한 건과 진행 표시. 메모리에만 있고 잠금 때 지운다.

## 지켜야 할 조건과 테스트 (이 목록을 먼저 테스트로 쓴다)
**등록 폴더 밖은 읽지도 쓰지도 않는다**
- 목록이 비어 있으면 두 도구 모두 거부하고 PC 파일 시스템 호출이 없다
- 폴더 밖 절대 경로, `..` 로 나가는 경로, 이름만 앞부분이 같은 이웃 폴더(`C:\work` 와 `C:\work2`), 대소문자만 다른 경로, 다른 드라이브
- 폴더 안의 링크·정션이 밖을 가리키면 거부 (실제 경로 기준)
- 사용자 데이터 폴더 안이면 거부. 그 폴더를 포함하는 폴더는 등록이 거부된다
- UNC, 장치 경로, 대체 데이터 스트림, 예약 이름, 상대 경로는 거부
- 폴더 밖 경로는 파일이 있을 때와 없을 때 오류가 같다
- 렌더러의 설정 변경 요청으로 `transferRoots` 를 바꿀 수 없다

**확인 없이 전송하지 않는다**
- 알림 수준이 무엇이든 확인 창을 거친다
- 거부·만료·취소·확인 중 잠금 → 임시 파일 생성과 전송 호출이 없다
- 허용 뒤 세션의 `mcpEnabled` 가 꺼졌으면 전송하지 않는다

**보여 준 것과 전송하는 것이 같다**
- 확인 창의 양쪽 경로·크기와 실제 전송 인자가 같다
- 허용 뒤 보내는 파일의 크기·수정 시각이 달라졌으면 보내지 않는다. 전송 중에 달라졌으면 실패하고 임시 파일을 지운다
- 보내는 파일은 조사 때 연 핸들에서 읽는다 (경로를 다시 열지 않는다)
- 받는 쪽 원래 파일이 확인 창 뒤에 생기거나 바뀌었으면 이름을 바꾸지 않는다
- 서버 심볼릭 링크: 확인 창과 쓰기가 모두 실제 경로를 쓰고, 비밀 경로 이유가 실제 경로 기준으로 붙는다

**거부해야 하는 입력** (확인 창 없이 오류)
- 보내는 파일 없음, 폴더·장치·FIFO, 1GB 초과 (크기 0 으로 보이는 서버 파일은 읽다가 1GB 를 넘으면 중단)
- 받는 쪽 부모 폴더 없음, 받는 쪽 파일이 있는데 `overwrite` 아님, PC 의 받는 파일이 링크
- 서버의 `/proc`, `/sys`, `/dev`

**실패와 중지**
- 전송 중 실패·중지·제한 시간 → 임시 파일 삭제, 받는 쪽 원래 파일 그대로
- 잠금, MCP 끄기, 세션 허용 해제 → 전송 중지. 임시 파일 삭제가 끝난 뒤에 작업 종료를 보고한다
- 이름 바꾸기 실패 → 임시 파일 삭제, 결과에 이유
- 작업 개수 제한을 넘으면 시작하지 않는다
- 20초 안에 끝나면 결과를, 아니면 작업 ID 를 돌려준다

**밖으로 나가면 안 되는 것**
- 감사 로그에 파일 내용이 없다
- Claude 에게 가는 결과와 오류에 호스트 주소·계정이 없다
- 잠금 뒤 활동 목록에 전송 기록이 남지 않는다

**기존 동작 유지**
- 전송 중에도 같은 세션의 `run_command`, `write_file` 이 실행된다
- 기존 도구의 테스트가 그대로 통과한다

화면(확인 창, 설정의 폴더 목록)은 typecheck 와 실제 앱 확인 1회로 본다. 끝난 뒤 보안 검토 1회.

## 열어 둔 한계
- 서버에서 덮어쓰면 소유자가 접속 계정으로 바뀌고, ACL·SELinux 표지·하드 링크는 유지되지 않는다 (권한 비트는 유지).
- 기존 파일을 바꿔치기하는 SFTP 확장(`posix-rename`)이 없는 서버에서는 서버 파일을 덮어쓸 수 없다. 새 파일 올리기는 된다.
- 파일이 있는지, 크기가 얼마인지는 확인 없이 알려진다 (등록 폴더 안과 서버에 한함. 내용이 아니라 속성).
- 끊긴 전송을 이어받지 않는다. 처음부터 다시 보낸다.

## 설계에서 달라진 것
- 내려받기의 서버 파일은 확인 창 전에 연 핸들을 계속 들고 있지 않는다. 허용 뒤에 전송 채널에서 다시 열고, 실제 경로·크기·수정 시각이 확인 창에 보여 준 값과 같을 때만 읽는다. 확인 창을 기다리는 요청마다 SFTP 채널을 하나씩 잡지 않기 위해서다 (OpenSSH 는 연결당 채널 10개). 올리기의 PC 파일은 설계대로 조사 때 연 핸들만 읽는다.
- 제한 시간은 인자 없이 60분 고정이다.
- 확인 창을 기다리는 전송 요청은 4개까지다 (그보다 많으면 거부).

## 실제 프로토콜로 확인한 것
ssh2 서버 모드의 SFTP 테스트 서버(임시 폴더, 127.0.0.1)에 앱의 실제 `sessionGateway` 로 접속했다.
- 5MB 바이너리 올리기·내려받기: 내용과 SHA-256 이 같다 (각각 약 0.1초, 조각 320여 개를 겹쳐 보냄).
- 새 파일의 권한을 핸들로 644 로 맞춘다. 임시 파일이 남지 않는다.
- 같은 이름이 있으면 `overwrite` 없이는 거부한다. PC 쪽 덮어쓰기는 된다.
- posix-rename 이 없는 서버에서 서버 파일 덮어쓰기는 거부되고, 원래 파일과 폴더가 그대로다.
- 빈 파일, 없는 서버 파일, 등록 폴더 밖의 PC 파일.
- 느린 전송: 작업 ID 를 돌려주고, 같은 세션의 `run_command` 가 그동안 실행되고, `job_output` 에 진행이 보이고, `stop_job` 뒤에 임시 파일과 대상 파일이 없다.

확인하지 못한 것: 실제 OpenSSH 서버의 posix-rename 으로 기존 파일을 바꾸는 경로 (ssh2 테스트 서버는 이 확장을 알리지 않는다. 로직은 가짜 SFTP 테스트로만 확인).

## 보안 검토 반영
검토 결과: 확인 창을 거치지 않고 전송되는 경로는 없음. CRITICAL 없음, HIGH 2, MEDIUM 4, LOW 다수.

| 지적 | 반영 |
|---|---|
| H-1 등록 폴더를 지우고 같은 이름의 정션으로 다시 만들면, 정션이 가리키는 곳이 허용 범위가 됨 (재현됨) | 등록 폴더는 실제 경로로 저장되므로, 지금 풀어 본 실제 경로가 저장값과 다르면 그 폴더를 무시한다 |
| H-2 하드 링크로 등록 폴더 밖 파일을 올릴 수 있음 (경로 검사를 모두 통과, 재현됨) | 이름이 둘 이상인 파일(`nlink > 1`)은 올리기를 거부한다. 파일 ID 를 주지 않는 드라이브의 파일도 거부한다 |
| M-1 경로를 푼 뒤 파일을 열기 전에 중간 폴더를 정션으로 바꾸면 밖의 파일이 열림 | 연 뒤에 경로를 다시 풀어 같은 실제 경로인지 보고, 그 경로의 파일 ID 가 핸들과 같은지 비교한다 |
| M-2 내려받는 동안 받는 폴더를 바꾸면 이름 바꾸기가 다른 곳에서 일어남 | 제자리에 놓기 직전에 경로를 다시 풀어 확인한다 (Windows 는 열린 파일이 있는 폴더의 이름 바꾸기를 막아서 이 공격 자체가 실패한다) |

| L 중지와 제자리에 놓기가 겹치면 "원래 파일은 그대로" 라고 잘못 알림 | 놓는 단계는 끝까지 기다려 그 결과를 알리고, 기다려도 모르면 "확인하지 못함" 으로 알린다 |

반영하지 않은 것:
- `mcp.json` 을 직접 고쳐 등록 폴더를 넣는 경우: 읽을 때 다시 검증하지 않는다. 그 파일을 쓸 수 있으면 이미 앱 데이터 폴더를 쓸 수 있는 상태다. 앱 데이터 폴더 제외와 H-1 검사는 전송할 때마다 걸린다.
- 너무 넓은 폴더(`D:\` 전체, 시작 프로그램 폴더)를 등록할 때 경고하지 않는다.
- 앱이 비정상 종료되면 `.<이름>.ezshell-part-*` 가 PC 와 서버에 남는다. 시작할 때 청소하지 않는다.
- 디스크 여유를 미리 보지 않는다 (모자라면 실패하고 임시 파일을 지운다).
- 비밀 파일 경고는 이름 기준이라 이름을 바꾼 파일에는 붙지 않는다.
- 수정 시각이 2초 단위인 파일 시스템(FAT)에서는 크기가 같은 변경을 놓칠 수 있다.
- 렌더러가 침해되면 기존 SFTP 패널의 IPC(`sftp-download` / `sftp-upload`)로 PC 의 임의 경로를 읽고 쓸 수 있다. 이번 변경 이전부터 있던 것이고, 전송 폴더 제한은 MCP 쪽 요청에만 적용된다.
